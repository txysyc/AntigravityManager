# 版本与发行规范

## 三个号码的用途

| 名称 | 表示什么 | 维护位置 |
| --- | --- | --- |
| **管理器版本** | 用户下载和升级的 Windows 程序版本，用于 GitHub Release 标题、管理器标签和 EXE 文件名 | 根 `package.json` 的 `version` |
| **汉化补丁版本** | 管理器内置的汉化引擎与补丁内容版本，用于识别补丁、缓存和排查问题 | `engines/localization/package.json` 的 `version` |
| **Antigravity 版本** | 被管理的原应用版本，仅用于兼容性描述 | `engines/localization/profiles/*.json` 中经验证的版本及指纹 |

面向用户的程序发行只用管理器版本作为标题。发行说明另列内置补丁版本和已验证的 Antigravity 版本；补丁编号不跟随管理器编号，也不从目标应用版本推导。

## 如何递增

版本号是发行批次的标识。日常 Git 提交、PR 合并、修复和本地构建均不调整版本配置，提交类型只说明改动性质。等一批功能或修复达到可交付状态，再以最近一次公开发行作为基线，按两个组件各自的交付范围定版。同版本的开发验证产物使用独立输出目录，不覆盖已生成的产物；已经公开的发行版本与产物保持不变。

可参考 [Release Please 的发行 PR](https://github.com/googleapis/release-please/blob/main/docs/design.md#release-pull-request) 和 [Kubernetes 的发行周期](https://kubernetes.io/releases/release/#the-release-cycle)：日常变更持续合并，发行时统一整理更新记录、版本配置和标签。本项目沿用现有标签触发发布的工作流。

发行使用 [SemVer 2.0.0](https://semver.org/lang/zh-CN/) 的三段格式 `主版本.次版本.修订号`。`0.x` 是预览阶段；在此阶段，本项目用次版本标记功能新增或不兼容变化，用修订号标记兼容性修复。次版本增加时修订号归零。首次 `1.0.0` 需要明确稳定的配置、升级与恢复行为以及对外接口，并完成兼容性验证；进入稳定阶段后，不兼容变更递增受影响组件的主版本，次版本与修订号归零。

| 相比该组件上次发行的变化 | 管理器 | 汉化补丁 |
| --- | --- | --- |
| 仅维护源码文档、测试或规范，分发内容不变 | 不变 | 不变 |
| 修复管理器现有功能、界面或打包；补丁内容不变 | 修订号 | 不变 |
| 增加向下兼容的管理器功能；补丁内容不变 | 次版本 | 不变 |
| 修复翻译或补丁行为，支持的 Antigravity 版本范围不变 | 若随新管理器 EXE 一起发布，至少升修订号 | 修订号 |
| 新增经过验证的 Antigravity 版本支持，或新增兼容的补丁能力 | 不因此升次版本；若仅随新 EXE 分发补丁，发版时升修订号 | 次版本 |
| 引入不兼容的配置、数据、接口或补丁机制变化 | 受影响的 `0.x` 组件升次版本，稳定组件升主版本；发行说明必须写清迁移与恢复方式 | 同左 |

同一 Antigravity 版本内新增一个经验证的构建指纹，按补丁兼容性修复处理。支持新的 Antigravity 版本属于汉化补丁的能力新增；管理器只在自身新增功能或有不兼容变化时考虑升次版本，内置补丁更新不会联动升次版本。只更新汉化补丁时，已有管理器发行文件及其内置补丁不变。一次发行包含多类改动时，每个组件各取所需的最高递增级别，不按提交数或改动文件数叠加。

## 定版与保留

1. 对照各组件最新的对应标签，确认哪些用户可见行为、兼容范围或分发内容发生变化，再决定升哪一位。
2. 同步版本配置、更新记录与实际支持范围。构建后核对程序版本、EXE 文件名和内置补丁版本；补丁版本变化时重新验证产物指纹和安装恢复链路。
3. 管理器使用 `manager-v<版本>`，补丁使用 `localization-v<版本>`。只有两者都有新版本时才同时创建新标签；历史 `v0.4.1` 保持原名。面向用户的管理器 Release 使用管理器标签。
4. 公开过的版本号、标签指向和发行包内容保持不变。后续若分发内容改变，按上表选择新版本。提交、打标签和推送仍遵循 [协作规范](../AGENTS.md) 的授权要求；操作见 [开发指南](../docs/development.md#发布)。
5. 推送新的管理器标签时，GitHub Actions 对标签提交运行 CI，核对标签与源码版本，再发布 Windows x64 EXE、SHA-256 校验文件和对应更新记录。标签必须指向包含工作流的提交；主分支推送与补丁标签不触发管理器发行。CI 不使用第三方原始样本，发行前仍需按改动范围完成 [本地验证](../docs/testing.md)。
   普通 CI 可取消同一分支或同一 PR 上过时的测试，但不得取消发行标签调用的测试。

经确认重建发行版本线时，从选定的基线维护新的更新记录和版本递增规则。旧发行的版本标识和安装记录保留原样；历史资料可继续用于排查和恢复。汉化产物的版本身份与指纹须同步重建和核验，不能把旧补丁直接改名为新版本。

## 发行说明

[CHANGELOG.md](../CHANGELOG.md) 是管理器更新记录和 GitHub Release 正文的共同来源。按当前版本线从新到旧排列，每个版本只有一个二级标题：`## 0.2.0`，已确定发布日期时可写成 `## 0.2.0 - YYYY-MM-DD`。版本线的基线可以列入更新记录；开发过程记录放在 `docs/`。

- `### 主要变化`：至少一条用户可见的改动，先写影响最大的新增、修复或兼容变化。
- `### 兼容性`：使用列表项 `内置汉化补丁：` 和 `已验证的 Antigravity 版本：`。版本用行内代码标记，多个应用版本按升序用顿号分隔，与补丁配置和兼容配置保持一致。
- 按需写 `### 下载与使用` 或 `### 升级提示`。验证范围、已知限制和迁移步骤优先用简短文字说明。只有用户确实需要进一步操作时才链接已公开的文档；不引用本地报告或验证产物。

工作流校验并取出当前版本的正文，不带版本标题。若需引用随源码公开的 Markdown 文档，使用相对仓库根目录的链接，工作流会将它指向发行提交。发行前可按[开发指南](../docs/development.md#发布)预览。
